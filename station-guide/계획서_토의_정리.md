## 2. 계획서 메모에서 남은 쟁점

- **현재 위치 표시**: 직관성을 위해 필요하다는 의견. 지하에서는 GPS가 안 돼서 처음부터 빠졌다. 방법을 찾으면 넣기로 함.
- **표지판 사진으로 위치 추정**: GPT 웹에 군자역 사진을 주니 역 이름은 맞혔다. 다만 역을 맞히는 일(GPS로도 가능)과 역 안의 어느 지점인지 맞히는 일은 다른 문제라서, 범용 모델로 지점까지 맞힐 수 있는지는 해 봐야 안다.
- **사진 비교 방식**: 학습은 필요 없다. 등록 사진을 미리 임베딩(Gemini Embedding 2 등)해서 DB에 저장해 두고, 사용자 사진 한 장만 임베딩해 유사도를 계산하면 된다. 결국 지점별 사진은 미리 찍어 둬야 한다.

## 3. 카톡 토의 (장상욱)

**진행 방식**
- 지금은 merge 없이 각자 코딩 에이전트로 만들어 보고, 괜찮은 방법을 고른다.
- 해커톤 현장에서는 에이전트를 각자 하나씩 쓴다(토큰 부족 때문). 방법론이 정해지면 기능을 나눠서 merge한다.
- 역 하나를 3D로 모델링하는 프로토타입 형식으로 간다.

**장상욱이 막막하다고 한 부분 = 방법론**
1. 어떤 기준으로 기준점을 잡는가
2. 노드를 어떻게 뽑고 그래프를 어떻게 구축하는가
3. 기준점을 3D로 어떻게 만드는가
4. 그 3D가 현실과 얼마나 비슷한지 어떻게 확인하는가

**장상욱의 현재 방법론 (`3D_roadMap`, 군자역)**
1. 역사 안내도로 3D 모델링
2. 3D 모델 확인
3. 개찰구·엘리베이터·화장실·기둥·매표기를 모듈로 만들어 안내도 기준으로 배치
4. 1인칭 시점 제작
5. 기준점 노드를 뽑아 그래프 생성
6. 최단경로 계산
7. 실제 사진·영상으로 디테일 추가

- 외부 데이터(공공 CSV, API)는 넣지 않았다. 처음에 넣어 봤더니 활용을 많이 못 해서, 이번에는 단계를 나눠 조금씩 진행 중.
- 기준점 후보는 모듈화한 엘리베이터·개찰구·화장실·기둥·매표기.
- **현재 구현물에서는 기준점(시설물)을 노드로 잡지 않았다.** 경로를 먼저 뽑고, **방향이 바뀌는 지점을 노드**로 잡았다.

## 4. 이 세션에서 확인한 사실

- `3D_roadMap` 웹 화면은 동작한다. 경로 보기, 재생(다음 확인 지점까지), 도착했어요, 속도, 층 보기, 확대 모두 작동. 1× 이동 속도가 초당 12m라 구간이 1~3초 만에 끝난다. 화면은 한국어만 있다.
- 개찰구 위치는 안내도, 외형은 `gunja1.mp4` 참고. 7·8번 쪽 개찰구 하나만 영상과 대조했고, 개수·간격·치수는 모형 값.
- 공공 데이터(`data.zip`)에는 역 내부 구조물 좌표가 없다. 쓸 만한 것은 지하도 노드 31개(위경도, 층 없음), 환승 빠른 칸·문 번호, 상가 업종·번호(편의점 725-101), 층수·깊이·면적.
- 웹에서는 가속도·자이로 사용 가능(아이폰은 권한 버튼 필요). 와이파이·블루투스 스캔과 기압계는 불가(브라우저별 지원은 미확인).
- 구조물 정보는 경로를 따라 걸으며 촬영 → 프레임에서 Gemini로 후보 추출 → 사람이 검수해 노드에 붙이는 방식이 현실적이다.

## 5. 정리가 필요한 충돌

- `방안정리.md`의 최종안(걸음 추적 PDR + 갈림길에서 "이 모습인가요?" 확인)과 계획서 시나리오(도착 버튼 + 표지판 사진 LLM 추정)가 다르다. 어느 쪽을 기본으로 할지 정해야 한다.
- 노드 기준: 장상욱 구현은 "방향 전환점", 토의에서 원하는 것은 "현실에서 알아볼 수 있는 기준점(시설물)". 둘을 어떻게 합칠지 정해야 한다.
- 현실과의 유사도를 무엇으로 잴지(현장 사진 대조, 걸음 수 대조, 안내도 겹쳐 보기 등) 아직 기준이 없다.
